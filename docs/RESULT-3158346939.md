## 2. Pipeline

1. **Capture**: headful Chrome against a managed Turnstile page. Raw captures stay outside the repo.
2. **Boot and instrument**: `tools/deob-auto/lib/vm-harness.mjs` runs the orchestrator in a Node `vm`
   sandbox with network globals disabled, and instruments the opcode dispatcher.
3. **Disassemble**: `lib/disasm.mjs` plus Chrome-seeded traces give the stage1/stage2 listings. Opcode,
   length and successors come from executing the real handlers.
4. **Lift**: `lift-exec.mjs` / `build-subst-table.mjs` emit the per-op substitute table, and
   `compile-fn-bodies-h128.mjs` compiles function bodies (`subst-tab-h128.json`, stage2 `fnBodies` 314).
   H130: the same compiler on stage1 (`H130_STAGE=1` derive / call-mode / pin passes), merged by
   `merge-stage1-fnbodies-h130.mjs` into `subst-tab-h130.json` (stage1 bodies under `s1|hpc:hkey`, 10).
5. **Readable render**: `readable-h122/stage{1,2}.verified-flow.js`, which is split per function into `final/`.
6. **Runtime substitution**: `tools/chrome-run/lift-subst-runtime.js`, injected by `run-plain.mjs`.
   Two modes: `subst` (lifted code only) and `shadowcmp` (native handler, restore, lifted, compare per step).
   CF script bytes are never modified; substitution happens in the environment only. Runs are offline.

### 3.3 Orchestrator: executed instrumented readable + colFit (H117 method)

Gate classification: **executed instrumented readable text + colFit column anchoring**. The
served text is the instrumented, column-anchored form of the committed readable, related byte for byte by:

1. `orch-exec-h130.mjs <orch.dat> <readable> <pins> [--posmap <map>|--check]` produces
   `final/orchestrator.readable.js` (copy of `out/3158346939/int-plain-1.orchestrator.exec-h130.readable.js`):
   sha256 `7a1a0b75be45a0cfafb9e8e309f2c28d3f45c294db1ea685dd37db9450b0b89e`, 514195 bytes. Same normalize + pretty-print as the
   H129 readable. 124 sensitive literals are replaced by `globalThis[Symbol.for("deob.orchPin")][i]`.
   `--check` regenerates it from the capture and compares bytes.
2. `run-plain.mjs` reads it (`RUN_ORCH_READABLE`), requires the posmap's sha256 to equal the
   readable's sha256 (`RUN_ORCH_STACKMAP`), and installs the pin table (`RUN_ORCH_PINS`, local only).
3. `page.mjs buildInstrumentedHtml(orchText, orchPosMap)` applies a deterministic transform:
   `instrument(text, {map, colFit, comments:false})` → map entries re-pointed through the posmap at
   the original VM line:col → `injectEncryptHooks` → `anchorColumns(original VM text, …)`. Tokens
   land at the original page columns, so CF's own `Error.prepareStackTrace` capture reads
   the original positions with no override. Each run records `orchReadable`
   `{sha256, bytes, applied:true, form:"instrumented + colFit(original columns)"}`.
4. Baseline (`RUN_RAW`) labels serve the captured page (`applied:false`).

`RUN_ORCH_RAWDIAG=1` (with `RUN_RAW` + `RUN_ORCH_STACKMAP`) is **diagnostic-only**, off by default
and never part of any gate. It serves the verbatim readable with an `Error.prepareStackTrace`
frame remap. That breaks the project rule (CF installs and hashes its own prepareStackTrace).

### 5.1 Variation root causes (H130/H131, by execution)

- **native**: the H129 "no output" was a harness bug. `run-plain.mjs` computed the breakpoint
  positions (`BP_SITES`) before splicing the inline `RUN_HOOK` source into the page, so the
  output-capture breakpoint resolved at a stale column and never fired. H130 takes the positions from the
  final served html. Now baseline = subst = `4de65633c1c6` (plainLen 74048), fnFail 0 / fnBoth 0.
- **noworker**: a deliberate CF bail, not a harness bug. `RUN_BP_DIAG` hits: worker try entered →
  `new zW.Worker(…)` throws `TypeError: zW.Worker is not a constructor` → catch → reject; the post-worker
  step is never reached and the VM runs 0 instructions. The page reports reason `unsupported_browser`.
  No payload exists in any mode, so the harness timeout is the expected outcome.
- **canvas_noread**: a lift coverage gap on the canvas-readback-failure path, which no golden run
  takes. Baseline, tracebase and shadowcmp agree (shadowcmp 0 miss / 0 err). Subst fails inside
  `fn_canvas_getImageData_56911`: 9 fn bodies fail (fnFail 9, all fnBoth). The CF retry then reloads the widget, so no payload is produced. H130 added three
  real-handler derivation rules, each self-checked against the captured stage2 table
  (`H130_RETCHK`):
  - op245 return: 680 entries checked. 636 are byte-same. The other 44 differ only because the captured entry
    writes a constant-folded value in place of `R(205)`; the register, `RET` tag and frame pop are the same.
  - op160/161 branch: 1348/1348 same (1149 + 199).
  - op199/210 keyed property store: 1251/1251 same. With trace-seeded prefix sites (`H130_TRACE`) the first failure moved
  from @57928 op199 (no-write lift) to **@58022 op200** (call): the derived successor (58026:27)
  differs from the live one (58027:27). These candidate derivations
  (`derived-sites-h130.json`) are **not** in `subst-tab-h130.json` and are not gated.

  **H131 closed it** (`subst-tab-h131.json`, details in build doc §H131):
  - op200 @58022 was not the fault. Lookup keys are pre-fetch keys (`hk = (nextPc+1):nextKy`), so derived 58026 and
    live 58027 name the same successor. The failing step was **58027:128 op138 in apply form**
    (`rDst = rF.call(rThis, …)`), which the H130 op138 rule did not cover. New rules: op138 member and apply forms
    (`H131_138CHK`: 1343 same as captured; the 51 others differ only in which register is read, where the capture named
    a register by its observed value), and op53 jump (`H131_53CHK` 4070/4070).
  - The VM throw rule now applies to every fn body, including fns with no try/throw op (`getImageData` throws natively
    on the read-blocked canvas): fnCatch 604, fnEsc 3.
  - Root cause of the last failures: `liftFlow` fitted op103/op26 as pure register writes and dropped the store
    `R(o)[R(k)] = c`, because numeric runs ignore stores on number registers and the proxy had no `set` trap.
    Fix: effect traps, an `x-effect` check, and a `liftStore` form (`H131_XCHK` on op103/op26: 829 same, plus 580 that
    differ only by a literal the capture inlined, 0 diff).
  - Result: baseline = subst = tracebase `a8317f7c964e` (plainLen 64432) at T1/T2/T4. fnFail / fnBoth / fnPartial /
    fnEntryFb / fnMidAssert 0. SC miss 0 / err 0, probeFail 4.
  - No `[-]` arm closes. The 92 step keys only canvas_noread reaches sit in try-handler regions
    (`fn_canvas_getImageData_56911` 48, `probe_38_hMYS1` 20, other getImageData fns 24) that `readable-h122` does not
    render. They run from per-op table entries (92/92 in h131, 31/92 in h130) and are checked by the sha and SC.
  - H132 renders those regions as catch blocks; all 92 keys appear with `[L c…]` marks.
